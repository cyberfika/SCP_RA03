Modelagem do Problema
Minimum Set Cover sobre combinações binárias

Universo e Conjuntos

U = {1, 2, ..., 25}

S₁₅ = C(25,15) = 3.268.760 subconjuntos de tamanho 15

Sₚ = C(25,p)    p ∈ {14, 13, 12, 11}

Objetivo Formal

Para cada p, encontrar SB₁₅,ₚ ⊆ S₁₅ tal que:

∀ Y ∈ Sₚ, ∃ X ∈ SB₁₅,ₚ : Y ⊆ X

Classificação

Instância de Minimum Set Cover — NP-difícil

Nenhum algoritmo polinomial exato é conhecido (a menos que P=NP)

Formulação ILP (Programação Linear Inteira)

LP = variáveis contínuas xᵢ ∈ [0,1] → relaxação convexa

ILP = variáveis binárias xᵢ ∈ {0,1} → exato, mas NP-difícil

xᵢ ∈ {0,1} ∀ Xᵢ ∈ S₁₅ minimizar: Σ xᵢ sujeito a: Σ_{i: Y⊆Xᵢ} xᵢ ≥ 1 ∀ Y ∈ Sₚ

LP — Relaxação Contínua

  • xᵢ ∈ [0,1] — programação linear
  • Solúvel em tempo polinomial (Simplex/IPM)
  • Fornece lower bound (LB-LP)
  • Não garante solução inteira válida

ILP — Programação Linear Inteira

  • xᵢ ∈ {0,1} — variáveis binárias
  • Exato: encontra SB mínimo global
  • NP-difícil: inviável em escala completa
  • Estratégia: ILP pós-greedy sobre candidatos reduzidos (solver disponível)

Lower Bounds — Critério de Qualidade
Limites inferiores para |SB₁₅,ₚ|

LB-LP (contagem direta)

Cada X ∈ S₁₅ cobre exatamente C(15,p) subconjuntos de tamanho p.

|SB| ≥ ⌈ C(25,p) / C(15,p) ⌉

Mesmo limite que a relaxação LP fornece.

Cota de Schönheim

Limite combinatório derivado da teoria de covering codes.

Sempre: LB-Sch ≥ LB-LP

Garantia Teórica do Greedy

|SB_greedy| ≤ H(|Sₚ|) × |OPT|

H(n) ≈ ln(n) + 0,577  →  H(5.200.300) ≈ 15,4

Na prática: gap de 1,79× a 3,78× (4–9× melhor que o pior caso teórico)

Estruturas de Dados
Representação eficiente de subconjuntos de U = {1..25}

Bitmask uint32

Cada subconjunto de U → inteiro de 25 bits (uint32)

{1,3,5} → bit 0, bit 2, bit 4 → 0b10101 = 21

Teste Y ⊆ X em O(1):   (X & Y) == Y

Índices e Arrays

  • s15_index: bitmask → índice em S₁₅   O(1)
  • sp_index: bitmask → índice em Sₚ     O(1)
  • count[]: int32[|S₁₅|] — cobertura atual de cada X
  • nao_coberto[]: bool[|Sₚ|] — alvos pendentes
  • Arrays NumPy uint32 — operações vetorizadas

Seleção de estratégia (argmax de count[])

  • p=14, p=13 → Heap lazy (poucas atualizações/iter)
  • p=12      → np.argmax (volume médio)
  • p=11      → Atualização paralela de count[]

Heap Lazy (max-heap com entradas obsoletas)

heap = [(-count_inicial, i) for i in range(N)] heapify(heap) # Extrai o máximo válido: while True: neg_cnt, i = heappop(heap) if count[i] == -neg_cnt: break # válido

Algoritmo Greedy para Set Cover
Aproximação gulosa com garantia teórica logarítmica

Pseudocódigo

Entrada: S₁₅, Sₚ Pré-proc: construir s15_index, sp_index, count[], nao_coberto[] SB ← ∅ enquanto existir alvo não coberto: X* ← argmax count[X] // máximo atual SB ← SB ∪ {X*}; count[X*] ← −1 para cada Y ⊆ X*, |Y| = p: se Y não coberto: marcar Y como coberto para cada X ∋ Y: count[X] ← count[X] − 1 retornar SB

Garantia de Aproximação

|SB_greedy| ≤ H(|Sₚ|) × |OPT|

H(n) = ln(n) + γ,   γ ≈ 0,577 (constante de Euler)

H(5.200.300) ≈ 15,4

→ greedy garante solução ≤ 15,4× o ótimo global

→ na prática: 1,79× a 3,78× (muito melhor)

Complexidade de Tempo

Θ( K × C(k,p) × C(n−p, k−p) × log N₁₅ )

K = |SB|,   gargalo = atualização de count[]

Complexidade de Espaço

O(N₁₅ + Nₚ) → O(C(25,15) + C(25,p))

O greedy não garante solução ótima global

Encontra solução aproximada de qualidade mensurada pelo gap vs LB

Programa 1 — Geração

  • Θ(C(n,p)) por conjunto — itertools.combinations
  • Espaço: O(C(n,p)) — array uint32 completo
  • Sequencial: ~80s | Paralelo: ~18,7s | Speedup: ~4,3×

Programas 2–5 — Greedy Set Cover

  • Gargalo: atualização de count[] (A updates/iter)
  • Pré-proc: O(N₁₅ + Nₚ) — construção dos índices hash
  • Θ(K × A × log N₁₅) com heap  |  Θ(K × (A + N₁₅)) com argmax
  • Espaço: O(N₁₅ + Nₚ) ≈ O(8,5M) uint32 ≈ 34 MB/instância

Comparação Ω, Θ, O

Ω: melhor caso — SB cobre tudo logo no início (improvável)  |  Θ: caso médio com distribuição uniforme de Sₚ  |  O: pior caso — greedy precisa de |Sₚ| iterações

Na prática: K << |Sₚ|  |  Para p=11: K=12.733 vs Nₚ=4.457.400 (0,3% do pior caso)

Gargalos Computacionais e Paralelismo
Onde o tempo é gasto e onde o paralelismo compensa

Programa 1 — Geração Paralela ✓

  • 5 conjuntos (S₁₁..S₁₅) são independentes entre si
  • multiprocessing.Pool.map → 5 workers simultâneos
  • Sequencial: ~80s  |  Paralelo: ~18,7s
  • Speedup observado: ~4,3×
  • Overhead Windows (spawn): mais lento que Linux (fork)

Programa 5 (p=11) — Atualização Paralela ✓

  • 1.366.365 updates/iter → volume justifica overhead IPC
  • Estratégia: Pool criado uma vez antes do loop
  • Workers decrementam count[] em batches de Y's
  • Argmax permanece sequencial (depende do count[] completo)

Critério: paralelizar quando updates/iter >> custo de IPC (~10k–100k threshold)

Por que p=14, 13, 12 não foram paralelizados?


p=14 → 165 updates/iter

  • IPC overhead >> trabalho útil por iteração
  • Heap lazy já é eficiente: log(3,27M) ≈ 22 ops/extração

p=13 → 6.930 updates/iter

  • Volume ainda pequeno vs. custo de serialização IPC
  • Heap lazy ainda compensa

p=12 → 130.130 updates/iter

  • np.argmax vetorizado: O(N₁₅) ≈ 3,27M operações NumPy/iter
  • Borderline: NumPy puro + overhead IPC = empate ou ganho marginal

p=11 → 1.366.365 updates/iter ✓ paralelo

  • Volume suficiente para amortizar overhead de IPC

Limitações e Possíveis Melhorias
Análise crítica da solução implementada

Limitações


  • ILP direto inviável em escala completa (n=25)
  • → 4,46 bilhões de coeficientes para p=11

  • Greedy não garante solução ótima global
  • → gap real de 1,79× a 3,78× vs LB-Sch

  • Auditoria exata p=14 é cara: ~2.373 B operações
  • → ~3,5h de verificação NumPy sequencial

  • Escalabilidade limitada para n > 27
  • → C(27,15) ≈ 21M; memória e tempo explodem

  • Tempo alto para p=13 (~3h) e p=11 (~3,4h)
  • → gargalo: atualização de count[] (A updates/iter)

  • ILP pós-greedy disponível, mas não executado em escala
  • → seria refinamento, não resultado principal

Melhorias Futuras


Algoritmos Exatos sobre Espaço Reduzido

  • ILP pós-greedy (candidatos do greedy como universo)
  • Branch and Bound / Branch-and-Price
  • Column Generation completo (B&P integrado)

Heurísticas Avançadas

  • Relaxação Lagrangiana para lower bounds mais apertados
  • Simulated Annealing pós-greedy
  • GRASP paralelo com mais restarts e busca local

Implementação de Alto Desempenho

  • Bitsets vetorizados (AVX2/AVX-512)
  • Cython ou C/C++ para gargalos Python
  • Distribuição em múltiplos processos/máquinas (MPI)

Auditoria Acelerada

  • Paralelizar audit_cobertura.py com batches de SB
  • GPU (CuPy) para verificação de cobertura massiva
